# 구현 가정과 결정

명세가 확정하지 않은 부분에는 단순성, 최소 권한, 개인정보 최소 노출 순서로 아래 기본값을 적용했다.

1. 활성 기수는 동시에 하나만 존재한다. 과거/예정 기수는 여러 개 가능하다.
2. profile의 `start_date`/`end_date`가 있으면 개인 실습 주차 계산에 우선하고, 없으면 cohort 날짜를 사용한다.
3. 멘토 배정은 기수별 이력으로 보존한다. 인턴 profile의 `cohort_id`와 배정 기수가 일치해야 한다.
4. 공지 신규 작성자는 ADMIN만 허용한다. 수정·삭제도 ADMIN으로 제한해 현재 명세의 작성자 조건을 포함하면서 운영 권한을 단순화했다.
5. 공지 댓글은 수정하지 않고 삭제 후 재작성한다. 본인과 ADMIN만 삭제할 수 있다.
6. 기수 대상 공지는 해당 기수 인턴과 그 기수에 실제 배정된 멘토, ADMIN에게 보인다.
7. 모든 사용자가 공개 일정과 게시판을 쓸 수 있다. 일정 수정/삭제는 작성자만 가능하며 ADMIN도 타인의 개인 To-do를 볼 수 없다.
8. 공지에서 만든 캘린더 일정은 공지 삭제 시 함께 삭제되고, 공지 변경 시 자동 동기화된다. 하루 단위 종료 시각은 KST 다음 날 00:00의 exclusive end로 저장한다.
9. 게시판 파일 최대 크기는 명세에 없어 50MB로 정했다. 공지/주간보고 첨부는 25MB다.
10. 주간보고 `weekly_feedback`은 인턴이 쓰는 주간 메모다. 멘토 피드백은 별도 상시평가에 기록한다.
11. ADMIN과 MENTOR는 주간보고 및 첨부를 읽기만 한다. 관리자 편의 목적이라도 DB write 권한을 부여하지 않는다.
12. 과제는 ADMIN과 현재 담당/서브 MENTOR가 수정·삭제할 수 있다. `assigned_by`와 대상 인턴/기수는 생성 후 바꿀 수 없다.
13. 상시평가는 MENTOR만 새로 작성한다. ADMIN은 평가 내용을 관리하거나 삭제하지 않고 최초 읽음 시각만 기록한다.
14. 익명 건의의 기술적 소유 관계는 `private` schema에 둔다. 제품 ADMIN은 익명 데이터만 조회한다. DB 프로젝트 소유자/service-role 접근까지 암호학적으로 숨기는 것은 이 구조의 범위가 아니다.
15. Auth 신규 사용자는 기본 `INTERN`, 비활성으로 생성한다. 실제 사용자 생성은 server-only Admin API 이후 ADMIN이 올바른 profile 속성을 설정하고 활성화하는 단일 서버 흐름으로 구현한다.
16. 삭제는 참조 무결성이 있는 핵심 업무 데이터에서 제한한다. 사용자 비활성화, 기수 완료, 평가/건의 취소를 우선한다.
17. 모든 업무 시각은 `timestamptz` UTC로 저장하고 화면은 `Asia/Seoul`로 표시한다. 날짜 전용 값은 `date`다.
18. 통합 프로젝트 조는 우선 profile의 확장 가능한 문자열 `project_group`으로 저장한다. 팀 공유 일지가 도입될 때 별도 project-group entity로 정규화한다.
